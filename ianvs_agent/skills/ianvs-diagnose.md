# Ianvs 失败诊断

1. 从当前 Run 确认实际命令、工作目录、解释器、配置快照、退出状态和最后真实阶段。读取原始异常链，区分直接失败条件与上游原因。
2. 沿 benchmark、testenv、算法 YAML 查找与当前异常有关的字段来源、模块注册与路径。README 和静态检查提供调查材料，不能新增验收要求；实际执行方式、模型和环境依据正式 Run 与环境记录，已有健康基线可通过正式引用核查。
3. 分别保存事实与假设。每条事实引用工具调用 ID、文件及行范围、Run 或独立检查记录；只新增或修正本轮观察，不重复复述旧事实。下一目标写下一项可执行动作，额外读取需要说明会影响当前修复决策的具体缺失证据。
4. 直接异常、相关源码和文件版本足够解释故障时，提交最小补丁。潜在后续错误留待修改后的真实运行确认，不需要把所有待验证猜测都变成修改前提。完整 read_file 返回的 file_version 为文件 SHA256，可与正式验收中同路径的冻结身份比较；优先使用已有完整读取。
5. 保持原始模型、数据、算法配置、指标和验收要求，允许修复引发异常的源码实现。申请审批时提供具体参数、修改依据及 Diff；程序执行后核查实际变化，随后使用新的 Run 执行原任务。
6. 原错误解除后出现新错误时，根据新运行证据继续调查；独立 Verifier 依据本轮完整 TestCase、产物、指标和必需检查判定结果。源码修改与运行成功均不能自行代替独立验收。
7. 旧 CSV、HTTP 正常响应、退出码为零以及模型自述均需要对应任务的其他验收证据。必需检查缺失或跳过时保持未验证；静态检查通过不表示该检查涉及的运行包装已在当前 Run 中启用。
8. 数据、模型、服务或授权无法合法取得时，保存阻塞原因、已有证据和可继续的条件。预算达到、取消与中断后保留任务状态和完整历史。
